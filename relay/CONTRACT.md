# Договор ретранслятора вебхуков Конспекта

Версия договора: **1**.

Конспект работает на компьютере, и у него нет публичного адреса: CRM и АТС
не могут прислать ему событие «звонок закончился». Ретранслятор — маленький
сервер, который ставит у себя сама компания. Он принимает вебхуки на
публичный адрес, сразу шифрует их ключом конкретного компьютера с
Конспектом и держит, пока Конспект не заберёт их исходящим запросом.

Этот документ — всё, что нужно, чтобы собрать ретранслятор на своём стеке.
Готовая реализация на Go лежит рядом (`main.go`); Конспекту всё равно, какая
реализация на той стороне, если договор соблюдён.

## Что видит ретранслятор, а что нет

- Тело вебхука он видит открытым только в момент приёма, в памяти. На диск
  оно ложится уже зашифрованным открытым ключом Конспекта. Взлом сервера
  не раскрывает накопленные события.
- Записи разговоров через ретранслятор не идут: в событии только ссылка,
  звук качает сам Конспект.
- Тела вебхуков не пишутся в журнал. Секретные пути в журнале скрыты.

## Термины

| Термин | Что это |
|---|---|
| Клиент | Один компьютер с Конспектом, привязанный к ретранслятору |
| Код привязки | Одноразовая строка, которую админ берёт из ретранслятора и вводит в Конспекте |
| Токен клиента | Секрет, которым Конспект подписывает свои запросы (`Authorization: Bearer …`) |
| Ключ клиента | Открытый ключ X25519 компьютера с Конспектом, 32 байта |
| Приёмник | Адрес вида `/h/<секрет>`, который вставляют в CRM или АТС |
| Событие | Один принятый вебхук, зашифрованный для клиента |

Все строки — UTF-8. Двоичные значения передаются в base64url **без** `=`.
Время — секунды Unix (число, может быть дробным).

## Шифрование

Запечатанный конверт libsodium: `crypto_box_seal` (X25519 + XSalsa20-Poly1305,
одноразовый ключ отправителя внутри конверта). Есть в любом языке:
PHP `sodium_crypto_box_seal`, Node `libsodium-wrappers`, Python `nacl.public.SealedBox`,
Go `golang.org/x/crypto/nacl/box.SealAnonymous`, Java/Kotlin `lazysodium`.

Ретранслятор запечатывает **открытым** ключом клиента; вскрыть может только
Конспект своим закрытым ключом, который не покидает компьютер.

Что внутри конверта — JSON:

```json
{
  "v": 1,
  "hook": "<id приёмника>",
  "kind": "bitrix",
  "received_at": 1791026525.123,
  "method": "POST",
  "content_type": "application/x-www-form-urlencoded",
  "query": "a=1&b=2",
  "body": "<тело запроса как пришло, base64url>"
}
```

## Адреса

Все ответы — JSON. Ошибки: `{"error": "<код>"}` и HTTP-статус из таблицы в
конце. Адреса `/v1/…` требуют `Authorization: Bearer <токен клиента>`, кроме
`/v1/pair` и `/v1/health`.

### `GET /v1/health`

```json
{"ok": true, "contract": 1, "impl": "konspekt-relay-go/1.0.0"}
```

Конспект проверяет `contract == 1` и отказывается работать с другим.

### `POST /v1/pair` — привязать компьютер

Запрос:

```json
{"code": "<код привязки>", "public_key": "<ключ клиента, base64url, 32 байта>", "name": "Ноутбук Анны"}
```

Ответ `200`:

```json
{"client_id": "<id>", "token": "<токен клиента, base64url, ≥ 32 байт>"}
```

- Код привязки одноразовый: после успешной привязки он больше не действует.
- Неверный или использованный код — `403 bad_code`. После 10 неудач подряд
  ретранслятор на 15 минут перестаёт принимать коды с этого адреса (`429`).
- Ключ не 32 байта — `400 bad_key`.

Как админ получает код, договор не задаёт. Готовая реализация печатает его в
журнал при запуске и выдаёт новый по `relay pair`.

### `POST /v1/hooks` — завести приёмник

Запрос:

```json
{"kind": "bitrix", "verify": {"application_token": "<токен приложения Битрикс24>"}}
```

`kind` — подсказка для Конспекта, как разбирать тело: `bitrix`, `amocrm`,
`mango`, `generic`. `verify` необязателен (см. «Проверка подлинности»).

Ответ `200`:

```json
{"id": "<id приёмника>", "path": "/h/<секрет, ≥ 32 байт base64url>"}
```

Полный адрес для CRM — адрес ретранслятора + `path`. Секрет в пути — единственная
защита приёмника от посторонних, поэтому он длинный и случайный.

### `GET /v1/hooks` — список приёмников клиента

```json
{"hooks": [{"id": "…", "kind": "bitrix", "path": "/h/…", "created_at": 1791026525}]}
```

### `DELETE /v1/hooks/{id}` — удалить приёмник

`200 {"ok": true}`. Приёмник сразу перестаёт принимать запросы (`404`).

### `POST|GET /h/{секрет}` — сам приёмник

Сюда стучится CRM или АТС. Ретранслятор:

1. Находит приёмник по секрету; нет такого — `404` без подробностей.
2. Принимает тело не больше **1 МБ**; больше — `413`.
3. Проверяет подлинность, если у приёмника задан `verify`; не прошла — `403`.
4. Запечатывает событие ключом клиента и сохраняет.
5. Отвечает `200 {"ok": true}` — быстро, чтобы провайдер не повторял запрос.

Не больше 20 запросов в секунду на приёмник (`429` сверх этого).

### `GET /v1/events?after=<id>&limit=<n>&wait=<сек>` — забрать события

- `after` — id последнего полученного события, пусто — с самого старого.
- `limit` — до 100, по умолчанию 50.
- `wait` — долгий опрос: если событий нет, ждать до `wait` секунд (до 30).

Ответ:

```json
{"events": [{"id": "01J9…", "hook": "…", "received_at": 1791026525.1, "sealed": "<конверт, base64url>"}]}
```

`id` растут по порядку прихода (ULID или аналог), сравниваются как строки.

### `POST /v1/events/ack` — подтвердить получение

```json
{"ids": ["01J9…", "01J9…"]}
```

`200 {"ok": true, "deleted": 2}`. Подтверждённые события удаляются с диска.
Неподтверждённые хранятся **7 дней** (настраивается), потом удаляются сами.
Если у клиента накопилось больше **10 000** событий, самые старые удаляются.

## Проверка подлинности вебхуков

Провайдеры, которые умеют доказать, что событие от них:

| `kind` | `verify` | Как проверять |
|---|---|---|
| `bitrix` | `application_token` | Поле `auth[application_token]` в теле формы совпадает с заданным |
| `generic` | `secret_header`, `secret_value` | Заголовок с этим именем совпадает со значением |

Сравнение — за постоянное время (`hmac.compare_digest`, `subtle.ConstantTimeCompare`).
У кого проверки нет (amoCRM), защищает только секрет в пути.

## Ошибки

| HTTP | `error` | Когда |
|---|---|---|
| 400 | `bad_request`, `bad_key` | Неразборчивый запрос, ключ не 32 байта |
| 401 | `no_token` | Нет или неверный `Authorization` |
| 403 | `bad_code`, `verify_failed` | Неверный код привязки; вебхук не прошёл проверку |
| 404 | `not_found` | Нет такого приёмника или события |
| 413 | `too_large` | Тело больше 1 МБ |
| 429 | `slow_down` | Слишком часто |
| 500 | `internal` | Что-то сломалось внутри |

## Требования к развёртыванию

- Только HTTPS снаружи. Готовая реализация сама получает сертификат Let's
  Encrypt по домену или работает за вашим nginx (`--behind-proxy`).
- Токены клиентов хранятся у ретранслятора хешем (SHA-256), не как есть.
- Журнал без тел вебхуков; секрет из пути `/h/…` в журнале заменяется на `/h/<скрыт>`.
