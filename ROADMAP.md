# Konspekt — умный блокнот для встреч

Локальный аналог Granola с упором на русский язык (GigaAM) и приватность.

## Принципы

1. **Максимально просто сейчас, расширяемо потом.** Каждая тяжёлая подсистема
   (захват звука, ASR, LLM-синтез) прячется за узким протоколом. В MVP —
   заглушка, дальше подменяется реализацией без правок UI.
2. **Локально по умолчанию.** Аудио и транскрипт не покидают машину, пока
   пользователь явно не включил облачный провайдер.
3. **Целимся в ONNX, а не в torch.** Даже если первый прототип на чём-то
   другом — интерфейс ASR обязан быть совместим с ONNX-рантаймом, иначе
   потом не отдерём зависимости и не соберём бинарник.

## Архитектура

```
konspekt/
  app/
    core/        события, конфиг, модели данных, шина
    audio/       захват: микрофон + WASAPI loopback  (этап 2)
    asr/         Transcriber: GigaAM ONNX | Whisper | Null  (этап 3)
    notes/       синтез заметок, шаблоны встреч  (этап 4)
    storage/     SQLite + файлы аудио
    ui/          pywebview окно + веб-фронт
    tray/        иконка в трее, горячие клавиши
  web/           статика фронта (HTML/CSS/JS, без сборки)
  models/        скачанные веса (в .gitignore)
```

Бэкенд и фронт общаются через JS-мост pywebview (`window.pywebview.api`)
плюс события сервер→клиент. HTTP-сервер не поднимаем: лишний порт, лишний
файрвол-попап, лишняя поверхность атаки.

## Этапы

### Этап 1 — Оболочка (готово)

Цель: окно поверх остальных, прячется в трей, визуально близко к Granola.
Звука и AI ещё нет — вместо них заглушки, но с настоящими интерфейсами.

- [x] Каркас проекта: `uv`, Python 3.12, зависимости, запуск одной командой
- [x] Окно pywebview: frameless, always-on-top, перетаскиваемое, запоминает
      позицию и размер
- [x] Трей (pystray): показать/скрыть, «Новая встреча», выход. Закрытие окна
      сворачивает в трей, а не завершает приложение
- [x] Глобальная горячая клавиша показать/скрыть
- [x] UI: список встреч слева, редактор заметок справа, панель записи сверху,
      таймер, кнопка старт/стоп
- [x] Редактор заметок с таймстемпами: каждая строка помнит момент встречи
- [x] Хранилище SQLite: встречи, заметки, (заготовка) сегменты транскрипта
- [x] Заглушки `AudioCapture` и `Transcriber`, отдающие фейковые данные,
      чтобы весь UI-поток проверялся целиком

### Этап 2 — Звук (готово)

- [x] Микрофон + WASAPI loopback раздельными дорожками (`soundcard`),
      сохранение в WAV 16 кГц моно
- [x] Индикатор уровня по реальному сигналу, выбор устройств в UI
- [x] Нарезка на чанки для распознавания (готовый вход для этапа 3)
- [x] VAD: отбрасывать тишину, чтобы не гонять её через ASR
      (сделано в этапе 3, см. «Поиск речи»)

### Этап 3 — Распознавание (готово)

- [x] GigaAM v3 CTC в ONNX через `onnx-asr`: только numpy и onnxruntime,
      без torch и NeMo. Веса int8, 214 МБ вместо 885 МБ у fp32
- [x] Скачивание модели прямо из приложения: прогресс, отмена, докачка
      после обрыва связи (проверено на настоящем разрыве)
- [x] Очередь распознавания в фоновом потоке: захват не ждёт модель,
      переполнение отбрасывает старое вместо роста памяти
- [x] Запись любой длины без дыр в расшифровке: если модель отстала
      и куски выпали, после «стоп» они досчитываются из сохранённого
      WAV и встают на своё место по времени. В окне видно, сколько
      осталось, а заметки ждут конца досчёта, чтобы не собираться
      по неполной расшифровке
- [x] Досчёт прошлой встречи не мешает новой: он держит запас
      мест в очереди под живую речь, а недосчитанное при закрытии
      программы запоминается, а не пропадает молча
- [x] Живой транскрипт в UI: реплики «я» и «собеседник» разделены по
      источнику звука, а не диаризацией, поэтому разделение точное
- [x] Поиск речи: тишина не попадает в модель, а фразы режутся по паузам,
      а не по границе куска. Порог считается от текущего фона, поэтому
      работает и на тихом микрофоне, и при гуле
- [x] GigaAM e2e вместо обычного CTC: пунктуация, заглавные буквы и числа
      цифрами при том же весе и той же скорости
- [x] Роутер языка: русский → GigaAM, остальное → Whisper base int8.
      Язык определяется по звуку (VoxLingua107), а не по тексту: текст к
      этому моменту уже испорчен кириллицей
- [x] Диаризация внутри дорожки: WeSpeaker ResNet34, 26 МБ ONNX. Работает
      и для нескольких собеседников в звонке, и для нескольких человек
      за одним компьютером

### Этап 7 — Режим диктовки (готово, задача №3)

Зажал клавишу, наговорил, отпустил — текст в активном поле любого
приложения. Ориентир Handy, но с GigaAM для русского: Handy работает на
Whisper и Parakeet, а Parakeet русского не знает вовсе.

- [x] Вставка текста в чужое окно: печать по буквам через `SendInput` и
      вставка через буфер обмена с возвратом прежнего содержимого
- [x] Своя горячая клавиша, два режима: держать, пока говоришь, и
      нажал/нажал ещё раз
- [x] Отдельный путь записи мимо встречи: звук живёт только в памяти,
      на диск не попадает и в базу не пишется
- [x] Модель держится прогретой, тишина по краям срезается
- [x] Полоска «слушаю» поверх всех окон, не крадущая фокус
      (`WS_EX_NOACTIVATE`)
- [x] Раздел в настройках: включение, сочетание, режим, способ вставки
- [x] Окна с правами администратора: Windows не пропускает туда ввод ни
      от одной программы, поэтому текст остаётся в буфере обмена и
      человеку об этом говорят

**Что оказалось неочевидным.** Три беды нашлись только на настоящем
Блокноте, ни одна не видна ни чтением кода, ни заглушкой.

Первая: структура `INPUT` объявлена по размеру клавиатурной части, 24
байта. Правильный размер — по самому большому варианту объединения, 32.
Windows сверяет переданный размер со своим и при несовпадении молча
отвергает весь ввод: ошибки нет, `SendInput` отвечает успехом, текст не
появляется.

Вторая: сплошной поток событий без пауз. «Привет, это диктовка. Ёжик,
42%!» приезжало как «Привет,!!!!!!!!!!!!!!!!». Отправка одним пакетом за
вызов не помогает вовсе, пауза в 12 мс на символ даёт точное совпадение.

Третья, в самой проверке: она не ждала фокуса и печатала в чужое окно,
оставаясь зелёной. По той же причине проверка однажды напечатала пробный
текст в открытый файл пользователя. Теперь Блокнот поднимается свой, со
своим временным файлом, и окно ищется строго по его имени.

**Выбор способа вставки.** По умолчанию буфер обмена, а не печать по
буквам. Замер на настоящем Блокноте: буфер доехал 6 раз из 6, печать 4
из 6, и на фразе печать занимает около секунды против мгновения.
Прежнее содержимое буфера возвращается на место. Кому это важнее
скорости, в настройках есть «печатать по буквам».

**Осознанный отказ.** Во время записи встречи диктовка не работает.
Модель одна, и распознавать два потока разом значит испортить оба:
встреча получит дыры, диктовка — задержку в секунды.

Что осталось на потом:

- [ ] Голосовые команды вроде «новая строка»
- [ ] Словарь пользователя для имён и терминов
- [ ] Linux: там нужны `xdotool` или `wtype`, Handy считает это
      нерешённым до сих пор

### Этап 20 — Группировка встреч (задача №21)

Теги вместо папок: встреча часто относится сразу к двум темам, папка
заставляет выбрать одну. Визуально можно показать деревом слева.

в запросе к базе, а не поверх готового списка. Автотеги от LLM
предлагаются, а не проставляются молча.

все установленные у людей копии ходят за обновлением в
`konspekt-releases`, и переезд релизов оставил бы их без обновлений
навсегда. Код и разработка живут в `konspekt`, дистрибутивы и разговор
с пользователями — в `konspekt-releases`.

**Снимки экрана делает `tools/снимки.py`, а не человек мышкой.** Он
поднимает окно на пустом временном профиле и наполняет выдуманной
встречей, поэтому личным данным на снимке взяться неоткуда физически.
Сфотографировать своё окно было бы быстрее, но там настоящие встречи и
имена коллег, а такой кадр не почистить задним числом: в углу списка
всегда что-нибудь останется. За целостностью следит
`страница_test.py` (снимки на месте и не пустые, все строки переведены
на все четыре языка), проверенный мутациями.

### Этап 22 — Публичная проверка релизов (частично, задача №23)

Konspekt пишет микрофон, слушает системный звук и перехватывает
горячие клавиши: со стороны это поведение шпионской программы, а
сборки PyInstaller и сами по себе ловят ложные срабатывания. Наш
отчёт «мы проверили» не стоит ничего, поэтому доказательства должны
быть внешними: ссылка на отчёт VirusTotal, подпись происхождения от
GitHub (`attest-build-provenance`, проверяется командой
`gh attestation verify`) и `SHA256SUMS`. Ссылку публиковать с любым
результатом: три красных и объяснение вызывают больше доверия, чем
ноль красных без ссылки.

**Это уже не теория.** Issue #4 в `konspekt-releases`: установщик не
запустился совсем, Windows показала «CreateProcess failed; code 225» —
файл заблокировал антивирус ещё до первого запуска. Человек при этом
видит не предупреждение, а неработающую программу, и никаких оснований
верить нам у него нет. Пока репутация сборки нулевая, такое будет
повторяться у каждого следующего.

Отсюда правило: на каждую жалобу такого рода отвечаем не уговорами, а
командами, которые человек выполнит сам и проверит нас, а не поверит.
`sha256sum -c SHA256SUMS` и `gh attestation verify`. Эти же команды
теперь лежат в README отдельным разделом, чтобы не искать их по
переписке.

- [x] `SHA256SUMS` считается при сборке и уезжает в релиз
- [x] Как проверить скачанное: инструкция на четырёх языках в публичном
      репозитории
- [x] Подпись происхождения отработала на 0.8.0 и проверена командой
      `gh attestation verify` на скачанном установщике
- [x] VirusTotal: ключ заведён, скан отработал, значок с числом тревог
      и ссылкой на отчёт стоит в описании релиза. Для уже выложенных
      релизов есть запуск по кнопке (`tools/отчёт_вирустотал.py`),
      сумма берётся из `SHA256SUMS` релиза, а не от свежей сборки:
      она не воспроизводима до байта, и отчёт вышел бы про файл,
      которого ни у кого нет. У 0.8.0 один движок из 75 насторожился,
      и так и написано.

**Ловушка с условием шага в Actions.** Шаг VirusTotal не запустился бы
никогда, даже с ключом: в его `if` стояла проверка `env.VT_API_KEY != ''`,
а `env`, объявленный в том же шаге, в его собственном условии не виден.
Условие всегда ложно, шаг всегда пропущен, и заметить это нельзя в
принципе — пропуск по ложному условию выглядит ровно так же, как
осознанный пропуск без ключа. Теперь наличие ключа выясняет отдельный
шаг `vt_key`, а его отсутствие пишется в сводку сборки словами.

Мораль шире одного шага: `if`, который тихо пропускает работу, обязан
объяснять причину пропуска. Иначе в CI заводится шаг-призрак, который
годами числится настроенным и ни разу не отрабатывает.

**Лимиты открылись 1 сентября, CI действительно запускается.** Но все
прогоны падали на первом же шаге: `uv sync --frozen` требует закоммиченный
`uv.lock`, а он был в `.gitignore` с самого начала — в репозитории его
никогда не было. Заодно вскрылось, что `pyinstaller` и `pywin32` (нужны
сборке установщика) стояли в рабочем окружении вручную, мимо `uv`, и не
были объявлены в `pyproject.toml` вовсе — с одним только `uv.lock` в
репозитории сборочный шаг всё равно бы упал. Починено: `uv.lock`
закоммичен, `pyinstaller`/`pywin32` переехали в dev-группу зависимостей.

**Первый релиз через CI проведён: 0.8.0, 9 сентября.** Сборка по тегу
собрала установщик, посчитала сумму, подписала происхождение и выложила
всё в публичный репозиторий. Проверено не по зелёной галочке, а
скачиванием: сумма сошлась, `gh attestation verify` подтвердил
происхождение. Перед этим пришлось чинить сам CI — он краснел с 7
сентября: README после перевода на английский потерял ссылку, за которой
следит проверка лицензий, а проверка окна диктовки ждала загрузки
страницы полминуты, чего холодному WebView2 на раннере не хватает.

**Ловушка с окружением.** Проверки запускать только через
`.venv\Scripts\python.exe run_tests.py`. Системный python видит не все
библиотеки, и десяток проверок падает с «нет такого модуля»: выглядит как
поломка кода, а на деле не тот python.

**Ловушка с PowerShell.** `Set-Content -Encoding UTF8` дописывает в начало
файла невидимую метку, и после этого `pyproject.toml` перестаёт читаться,
а вместе с ним падают проверки сборки. Правки в файлы вносить питоном или
редактором, а не через PowerShell.

**Ловушка при выпуске руками.** `gh release create` с файлами в конце
команды может создать релиз без единого файла и не сказать об этом:
страница выглядит нормальной, а скачивать нечего. Поэтому после выпуска
обязательно скачивать релиз обратно и сверять сумму, а не полагаться на
то, что команда завершилась без ошибки. На 0.5.0 это поймали.

Надёжнее выпускать в два шага: сначала `gh release create` без файлов,
потом `gh release upload`. Одной командой загрузка 60 МБ упирается в
таймаут TLS, и релиз молча не создаётся вовсе. На 0.5.5 так и вышло.

`latest.json` обновляется отдельно, иначе автообновление не увидит новую
версию: `python tools/обновить_latest.py "новость для окна"`. За этим
следит `version_test.py`, он краснеет, пока версия не опубликована.

Кроме оплаты для релиза по тегу нужен секрет `RELEASES_TOKEN` — токен с
правом записи только в `lamver/konspekt-releases`. Заведён 9 сентября,
права минимальные: Contents на один репозиторий, ничего больше.
Ключ `VT_API_KEY` необязателен: без него шаг VirusTotal пропускается,
но теперь громко — с пометкой в сводке сборки, а не молча.

**Зачем он всё-таки нужен.** Issue #4 в `konspekt-releases`: у человека
установщик не запустился вовсе, Windows выдала «CreateProcess failed;
code 225» — файл заблокировал антивирус. Это ложное срабатывание, и оно
будет повторяться, пока у сборки нулевая репутация. Ответить на такое
можно только внешними доказательствами: сумма, подпись происхождения и
ссылка на отчёт VirusTotal. Первые два у нас есть и проверены на 0.8.0,
третьего нет до появления ключа.

Секрет заведён 9 сентября, права минимальные: Contents на один
репозиторий, ничего больше. Первый выпуск через CI — 0.8.0.

**Оба репозитория теперь публичные, и исходный довод за их разделение
отпал**: он был в том, что Releases приватного репозитория отдаются
только по токену. Разделение оставлено сознательно, по другой причине:
все установленные у людей копии ходят за обновлением в
`konspekt-releases`, и переезд релизов оставил бы их без обновлений
навсегда. Код и разработка живут в `konspekt`, дистрибутивы и разговор
с пользователями — в `konspekt-releases`.

### Этап 25 — Качество распознавания вживую (задача №26)

Источник: issue lamver/konspekt-releases#2, «Плохо отрабатывает
транскрипция». Разобрано на боевой записи пользователя (170 реплик,
30.08). Две разные жалобы, чинятся по-разному, брать по порядку.

**Находка 1 (готово): определитель языка сходил с ума на короткой
русской речи.** Средняя фраза у пользователя — 1.2 с, а VoxLingua
надёжно угадывает язык только от ~2 с. Чисто русская встреча
размечалась 24 языками (`fr`, `pl`, `lt`, `ka`, `jw`, `gu`...), половина
фраз уходила в Whisper и превращалась в кашу: «и в транскрипт» →
`și le transcript.` (чешский). Порог уверенности поднят 0.5 → 0.85
(`app/asr/langid.py`), подтверждено `router_test.py` и боевыми
записями.

**Находка 1б (готово): язык на самой первой фразе встречи.** Если
определить нечего и вспомнить не у кого (нет истории дорожки), раньше
было жёстко зашитое `"ru"`. Теперь `LanguageRouter.fallback_lang`
берётся из `settings.asr.language` — готово к моменту, когда появится
не русскоязычный пользователь. Поле в настройках уже было, просто
нигде не читалось.

**Находка 2 (готово): ощущение «сказал — и тишина».** Причина была не
в VAD и не в модели, а в захвате звука: `AudioSettings.chunk_seconds`
стоял 5.0 — даже мгновенная фраза не попадала в VAD, пока из звуковой
карты не набирался целый пятисекундный блок. Снижено до 0.5 с, на
запись в WAV не влияет. Замер `latency_test.py`: задержка от конца
речи до готового текста была 1.8 с, стала отрицательной (текст готов
раньше, чем истекает пауза после фразы).

**Хвост находки 1б: крутилки для языка распознавания в интерфейсе
нет.** Обнаружено при доводке — экрана настроек в UI сейчас нет вообще
(ни `whisper_size`, ни что-либо ещё не редактируется пользователем).
`settings.asr.language` меняется только правкой файла настроек руками.
Не блокирует находку 1б: значение уже используется правильно, просто
пользователю неоткуда его выставить. Отдельная задача — завести экран
настроек, это больше одного вечера работы.

**Находка 3 (по итогам обсуждения): ручная коррекция языка фразы.**
Защитная сетка на то, что автоматика всё равно иногда промахнётся.
Пользователь кликает на неверно распознанную реплику, указывает
настоящий язык, модель пересчитывает этот кусок. В тот же интерфейсный
узел сразу закладывается кнопка «перевести на другой язык» для той же
фразы — задел на будущее, разговор двуязычный не редкость.
- [ ] UI: клик по реплике → выбор языка из списка → пересчёт через
      уже сохранённый `pcm` куска (нужно решить, храним ли исходный
      звук фразы для пересчёта или только офсеты в файле записи)
- [ ] Задел на перевод реплики — не делать сейчас, но не закрывать
      место в разметке интерфейса

**Находка 4 (готово): одна ошибка акустики заражала всю оставшуюся
встречу.** Найдено собственным замером на 3 минутах боевой записи в
реальном темпе речи (`latency_replay_test.py`): один 4-секундный кусок
акустика уверенно (0.93, выше поднятого в находке 1 порога 0.85)
распознала как литовский, и `_last[speaker]` держал это решение до
конца часовой встречи без пересмотра — 55 секунд русской речи ушли в
Whisper и превратились в кашу, заодно тормозя (7-15 с на фразу вместо
0.2-1 с в GigaAM). Порог уверенности защищает от неуверенных ошибок, не
от одной уверенной. Решение подсмотрено у Handy (`audio_toolkit/lang_id.rs`):
не доверять только акустике, а сверять её с языком уже готового текста
(`py3langid`, чистый Python, 0.17 мс на вызов). Если текст фразы (от
двух слов — короче ни звук, ни текст не отличают надёжно, проверено на
боевых репликах) явно кириллический, а акустика отправила её в чужую
модель — фраза и память дорожки чинятся сразу, ошибка не длится дальше
одной фразы. Ничего не привязано к одному языку: чинится расхождение
звук/текст, работает для любой пары языков одинаково, что и требовалось
для многоязычных встреч. Подтверждено интеграционным прогоном на том
самом куске записи, где нашли баг, и тестом в `router_test.py`.

**Находка 5 (готово, 0.6.0): обрубки фраз.** Вторая половина жалобы
пользователя («Пото.», «Усу.»), которую сначала отложили как «резку по
границе речи». Причин оказалось две, обе в `app/asr/vad.py`, обе не про
модель распознавания.

Первая: при речи без пауз дольше `MAX_SEGMENT` резать приходится, но
резали вслепую по таймеру — ровно посередине слова. В боевой базе таких
мест 172, видно прямо в тексте: «...добавить функцию» → «...когда
происходит в отчёте», «запустил...» → «П прогон по логам». Теперь
разрез ищется по самому тихому кадру в окне `QUIET_SEARCH` (стык слов,
вдох), и речь при этом не считается законченной — иначе остаток фразы
терялся бы целиком.

Вторая: `min_speech` сравнивался с длиной куска ВМЕСТЕ с `PAD` по 0.15с
с каждой стороны, поэтому хватало 0.05с звука, чтобы щелчок доехал до
модели и вернулся огрызком («са», «Д.», «ти»).

Замер на часе боевой записи, старый код против нового: мусорных реплик
31 → 0, резок вслепую 11 → 1, суммарная речь сохранилась. Закреплено
`vad_test.py` в `run_tests.py`; тест проверен на старом коде и падает
на нём (громкость в точке разреза 1.03 против 0.07).

**Находка 6 (готово, 0.6.0): обновления не доходили до тех, кто не
перезапускается.** Найдено при разборе вопроса «когда вообще работает
автообновление». Проверка версии звалась ровно один раз, из
`AppService.__init__`. Konspekt закрывают крестиком в трей, а не
выходом, и он может работать неделями: такой человек не получил бы ни
одного обновления, сколько их ни выпускай. Добавлен будильник
(`VersionChecker.watch`, `WAKE_INTERVAL` час), в сеть по-прежнему не
чаще `CHECK_INTERVAL`. Тест в `version_test.py` проверен на старом
коде и падает на нём.

**Находка 3 (готово, 0.6.1): ручная правка языка реплики.** Последний
пункт плана, обещанного пользователю. Наводишь на реплику, рядом со
временем код языка; выбрал нужный — программа берёт звук этого куска
записи (тем же путём, что кнопка «переслушать») и пересчитывает его
выбранной моделью. Нет записи, нет модели под язык, модель промолчала —
текст не трогается вовсе: испортить уже имеющееся хуже, чем не
исправить.

Проверено на боевых репликах, где Whisper зацикливался на русской речи:
«Если я буду птицей, то я буду птицей...» ×N, «Да нуууу...» → «Этих
тупеньких.» Тест `relang_test.py` в `run_tests.py` проверяет связку на
заглушках.

Здесь же пойман собственный промах: заглушка в тесте вешалась на
`service.asr`, поля с таким именем у `AppService` нет вовсе. Тест был
зелёный, а живая программа падала на первом же клике. Нашлось только
прогоном на настоящих данных. Теперь тест отдельно проверяет, что имя
поля совпадает с настоящим.

**Этап закрыт.** Все три пункта плана из issue №2 (каша из языков,
ручная коррекция, задержка) плюс обрубки фраз выпущены в 0.5.9-0.6.1 и
подтверждены на записи самого пользователя.

**Настройки распознавания в окне (готово).** Язык встреч и размер
Whisper были только в файле конфигурации; руками его правят единицы,
так что настройки фактически не существовало. Теперь это раздел
«Распознавание»: язык из списка, понимание чужой речи галочкой, выбор
модели с честной пометкой, что скачано, а что нет.

Применяется сразу: движок пересобирается на месте. Настройка, которая
срабатывает только после перезапуска, выглядит сломанной. Исключение —
идущая запись: там подмена ждёт остановки, иначе теряется накопленный
кусок звука.

Проверено `asrset_test.py` (двадцать пять проверок с обеих сторон моста)
и живым запуском окна: раздел открылся, смена языка дошла до настроек и
пережила перезапуск программы. Тест испытан девятью нарочными
поломками, каждая ловится.

**Долг закрыт выпуском 0.5.9.** Сборку пересобрали, и заодно
нашлась вторая половина той же беды: PyInstaller не клал не только
метаданные `py3langid`, но и его обученную модель `data/model.plzma` —
без неё сверка языка по тексту упала бы при первом же запуске у
пользователя, при том что в разработке всё зелёное. Обе части чинит
`packaging/konspekt.spec`, обе проверяет `bundle_test.py` отдельными
пунктами. Заодно выяснилось, что проверять сборку снаружи бесполезно:
код библиотек лежит внутри exe, и любой импорт в проверке молча берётся
из окружения разработчика. Теперь сборка проверяет себя изнутри сама
(`app/самопроверка.py`, ключ `--самопроверка`), и это ловит недостачу
по-настоящему.

### Этап 26 — Речь видно на ходу (0.7.0-0.7.1)

Продолжение того же issue №2. Пользователь обновился на 0.6.1 и написал:
«как была задержка, так и осталась». Был прав.

**Мерил не то.** В этапе 25 замер показал, что от конца речи до текста
проходит доли секунды, и я счёл задержку побеждённой. Но человек ждёт не
с конца фразы, а с начала: пока он говорит, экран пустой. Обработка
занимает 0.6 с (VAD 0.21 + GigaAM 0.42) — тормозило не распознавание, а
само устройство программы. По 4000 боевых реплик медиана фразы 2.7 с,
46% длиннее трёх секунд, ровно те «3-5 секунд» из жалобы.

**Решение: черновики.** `SpeechSegmenter.peek()` раз в секунду отдаёт
накопленное, не закрывая фразу; черновик идёт в очередь мимо базы, мимо
поиска говорящего и мимо саммари. В окне он бледнее, курсивом, с мигающей
чёрточкой: видно, что это догадка, а не расшифровка. Готовая реплика
встаёт на его место.

- [x] Потоковый показ речи, `draft_test.py` (26 проверок, испытан 11
      поломками)
- [x] Замер на боевой записи в живом окне с настоящей моделью: ожидание
      первого текста медиана 0.9 с, худшее 2.2 с, дольше трёх секунд — 0%

**Две ловушки нашлись только замером, не тестами.** `_peeked` считал
кадры буфера, который по ходу обрезается, поэтому черновики молчали и
первый замер дал нулевую выгоду. И `PAD` на черновике заставлял модель
ставить точку посреди слова.

**Промах 0.7.0: выпустил нерабочее.** `TRANSCRIPT_DRAFT` не было в
`FORWARDED_EVENTS` — событие не доходило до окна. Одна строка, и вся
работа этапа не видна пользователю. Тесты молчали, потому что звали
`showDraft` напрямую, минуя окно: двадцать шесть зелёных проверок на
полностью нерабочей программе.

Урок дороже самого бага: проверка, которая зовёт функцию напрямую, не
доказывает, что до неё доходит вызов. Проверять надо весь путь.
Закрыто тремя слоями: тест сверяет список пересылаемых событий и что
фронт не ждёт того, чего ему не шлют; сквозной прогон через настоящий
`MainWindow` (16 черновиков дошли до JS, было 0); самопроверка внутри
сборки стережёт ту же дорогу.

### Этап 27 — Задержка держалась настройкой, а не кодом (0.7.2)

Пользователь обновился на 0.7.1 и написал: «тоже не решило». Дал
посмотреть свою встречу 01.09 10:03. Разобрал базу и журнал вместо
догадок, и оказалось, что все три предыдущих выпуска были мимо.

**Причина не в коде.** В этапе 25 я снизил `chunk_seconds` с 5 до 0.5
секунды и считал вопрос закрытым. Но снизил я только значение по
умолчанию, а у каждого, кто запускал Konspekt раньше, это число уже
записано в `settings.json`. Файл настроек сильнее умолчания, поэтому
0.6.1, 0.7.0 и 0.7.1 не меняли давним пользователям ровным счётом
ничего: программа по-прежнему ждала пятисекундный кусок звука, прежде
чем вообще посмотреть на речь. Черновики из этапа 26 при этом честно
работали — просто выходили раз в пять секунд.

Замер на записи пользователя, оба значения в одном прогоне:

| | 5.0 (как у него) | 0.5 (как задумано) |
|---|---|---|
| ожидание, медиана | 1.5с | 0.4с |
| худшее | 6.4с | 2.1с |
| дольше 3с | 46% | 0% |
| текстов показано | 14 | 41 |

- [x] Унаследованное значение чинится при чтении настроек, один раз
- [x] Осознанный выбор пользователя не трогаем: правится только 5.0
- [x] `upgrade_test.py` читает настоящий старый `settings.json`,
      испытан поломкой
- [x] Самопроверка сборки стережёт то же самое (8 галочек)

**Урок, дороже предыдущего.** Умолчание в коде — это не то, что у
людей. У них лежит файл, и он старше моей правки. Меняя значение по
умолчанию, надо сразу спрашивать: а что будет у того, кто уже
пользуется? Мои замеры всё это время шли на чистых настройках, поэтому
показывали прекрасные цифры на программе, которая у живого человека
вела себя ровно как раньше.

**Заодно испортил пользователю установку.** Проверяя установщик 0.7.1,
я поставил его во временную папку, и он перехватил запись об установке
в реестре. Потом папку удалил — у человека осталась 0.5.9 и запись,
указывающая в никуда. Заметил при разборе, переустановил 0.7.1 в
штатное место. Проверять установщик надо на отдельной машине, а не на
рабочей.

### Сквозные задачи

- **Защита от регрессий (задача №17).** Функционал растёт, глазами
  уследить нельзя. Разделение быстрых и медленных проверок,
  GitHub Actions, проверки интерфейса, эталоны качества распознавания.
  Делать вместе с билдом, а не после.
- **Монетизация и интеграция с LLM (задача №19).** Решено. Локальная
  LLM бесплатна без ограничений: любая модель, какую тянет машина
  пользователя, класс железа определяем сами и предлагаем подходящую.
  Наш сервер LLM — софт бесплатен, платно только использование
  модели. Чужой провайдер по ключу (OpenAI, OpenRouter и прочие) —
  лицензия, около 50 долларов в год либо вечная. Мы берём деньги не
  за софт, а за уход к чужому провайдеру. Запись, распознавание,
  удаление, экспорт и шифрование бесплатны всегда. Считать локально
  через llama.cpp: один формат GGUF на все классы железа и сервер в
  формате OpenAI, поэтому слой LLM ходит и в локальную модель, и в
  наш сервер одним кодом. Слой абстракции над провайдером нужен с
  первой строчки этапа 4. Подробности в `docs/tasks/local-llm.md` и
  `docs/tasks/local-llm-tiers.md`.
- **Открытость кода и защита лицензии.** Решено. Наш exe
  декомпилируется за 10–15 минут, защиту от реверса не строим: это
  выброшенные дни, а секретов в дистрибутиве нет. Проверка лицензии
  живёт на сервере, в клиенте только запрос и показ ответа. Кто
  способен пересобрать и снять проверку, тот и так бы не заплатил;
  платят за удобство, а не за замок. Настоящая угроза не реверс, а
  чужая сборка под нашим именем, от неё защищает подпись
  происхождения (задача №23). Открытие кода держим как маркетинговый
  ход в рамках задачи №22. Подробности в
  `docs/tasks/openness-and-licensing.md`.
